# Local VLM support-relation feasibility — 4 October 2026

The optional vision-language stage now runs locally on the same 8 GB CUDA GPU as the geometric pipeline, with sequential model loading. It uses [Hugging Face's SmolVLM2-2.2B-Instruct](https://huggingface.co/HuggingFaceTB/SmolVLM2-2.2B-Instruct), pinned to revision `482adb537c021c86670beed01cd58990d01e72e4` with both weight hashes in the ignored local checkpoint `source.json`. The model card documents image/text input and a 5.2 GB video-inference memory figure; our image-only PyTorch measurement is below. This is a new implementation capability, not a novel relation model.

Before the first VLM inference, the [prompt and scoring protocol](results/smolvlm_relation_protocol.json) fixed twelve already reviewed SUN RGB-D laptop/table and bottle/table scenes, the annotated pair boxes, a single YES/NO/UNCERTAIN question, deterministic generation, and strict first-answer parsing. The model saw only RGB with the annotated child outlined red and annotated table green. No depth or 3D values entered the prompt. These scenes had been seen during other project work; the check is exploratory and uses oracle pair boxes.

| RGB paired relation | YES | NO | UNCERTAIN | Unparseable |
|---|---:|---:|---:|---:|
| Positive, 8 scenes | 6 | 1 | 1 | 0 |
| Negative, 4 scenes | 1 | 0 | 3 | 0 |

The [per-scene raw answers](results/smolvlm_laptop_bottle_relation12.json) and [count summary](results/smolvlm_relation12_summary.json) preserve the results. If only YES is accepted, two of eight positive relations are withheld and one of four negatives is accepted. The false YES was the annotated bottle/table pair in `sunrgbd_004139`, where the bottle visibly stands on a rear counter and the paired table is in the foreground. The VLM answered NO on a visibly supported laptop/table pair in `sunrgbd_001100`. Box prompts matter: with automatically detected boxes in that same positive scene, the VLM answered YES. These twelve prompts do not establish relation calibration or an independent accuracy estimate.

The VLM-only pass peaked at **4.876 GB PyTorch allocated** and **5.161 GB reserved**. A [full Grounding DINO → SAM → metric depth → VLM → correction run](outputs/bottle_table6_cli_vlm_advisory_000057.json) on one positive bottle/table image recorded YES and exactly reproduced the geometry-only camera-ray shift (−0.14187 m). Its [single-run profile](results/bottle_table6_cli_vlm_profile.json) measured **21.27 s total**, including **13.64 s** for VLM loading and judgment, with the same **5.161 GB VLM-stage reserved** peak. PyTorch's measurements exclude other GPU allocations and other processes; one image is not a latency distribution.

The main CLI exposes `--vlm-checkpoint checkpoints/smolvlm2-2.2b-instruct` as **advisory by default**. It stores each proposal's raw answer and parsed answer in the layout JSON, leaving the geometric proposal/correction unchanged. The experimental `--vlm-gate` retains only explicit YES judgments; it abstains if no unique candidate remains. On [scene 004139](outputs/bottle_table6_cli_vlm_gate_004139.json), two mask-contact proposals became one after VLM answers UNCERTAIN and YES, and the CLI applied a correction. The physical validity of the selected detected pair is unverified by the paired-table annotations. This illustrates why VLM gating is opt-in and cannot be presented as a validated improvement.

A subsequent [detected-box sensitivity check](results/smolvlm_detected_pair9.json) reused the exact model, prompt, and generation settings on all **nine of twelve** scenes where both annotated objects had detector matches. It was specified [after viewing the oracle-box answers](results/smolvlm_detected_pair_protocol.json), so it is explicitly post-hoc. Two answers changed when annotated boxes were replaced by matched detector boxes: the true laptop/table pair in `sunrgbd_001100` changed from NO to YES, while another true laptop/table pair in `sunrgbd_003070` changed from YES to UNCERTAIN. With detector boxes, five of seven matched positive pairs received YES and two received UNCERTAIN; both matched negative pairs received UNCERTAIN. The three missing-pair scenes remain in the coverage denominator and cannot be judged with this matched-pair protocol. These changes show box sensitivity, not a validated gain.

On those [identical nine matched pairs](results/smolvlm_detected_vs_geometry9.json), the mask-contact geometry gate accepted **7/7 positives and 0/2 negatives**, while VLM YES accepted **5/7 positives and 0/2 negatives**. Adding a hard VLM gate therefore lost two visibly true pairs without improving paired specificity in this small, previously inspected subset. The result supports the advisory default; it does not prove that geometry dominates on broader scenes or that every other detected proposal is correct.

Research next steps: annotate all plausible parent surfaces in a fresh room-aware sample; separate oracle-box VLM assessment from detected-box end-to-end assessment; compare geometry-only, VLM advisory, and VLM-gated correction on the same denominator; and develop an uncertainty rule that abstains on ambiguous support without simply dropping true relations. The current prompt and model are an implementation baseline, not the research contribution.
